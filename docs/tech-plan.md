# Справочник банкоматов — технический план MVP

Версия 0.2 · 23.10.2026 · основа: набор полей v0.2, итоги созвона 12.10.2026

Документ для разработки. Версия для заказчика — «План системы справочника банкоматов v0.2» (Word, хранится вне репозитория).

**Изменения v0.2:** полноценный вход по логину и паролю (вместо заглушки), карта банкоматов обязательна, сервис работает на сервере с автодеплоем после push.

## 1. Рамки

**Делаем:** веб-приложение «Справочник банкоматов» для банка X (Узбекистан): единый реестр банкоматов вместо Excel. Пользователи — бизнес и операционный блок. Сеть: ~1 000 банкоматов, через год ~1 300, через 3 года до 2 000.

**Ограничения:**

- Разработчик один, поэтому объём строго по MVP.
- Сервис работает на сервере (1 vCPU, 1 ГБ RAM, Ubuntu 22.04), доступ по IP. После push в `main` GitHub Actions собирает образы и обновляет сервер. На сервере ничего не собираем — памяти мало.
- Вход полноценный: у каждого сотрудника свой логин, пароль и роль. Сайт открыт в интернет, без входа данные не отдаются.
- Карта банкоматов обязательна.
- Реальных данных банка не будет. Заказчик не может передать свои Excel, поэтому все данные генерируем сами (раздел 6).
- Система не привязана к производителю: подходит для любых моделей.

**Не делаем в MVP:** внешний API для сайта и мобильного приложения, инкассации, захваченные карты, интеграции с процессингами и системами заявок вендоров, вход через единую систему учётных записей банка (SSO/AD), узбекскую локализацию.

## 3. Архитектура

```
Браузер (React SPA)
   │  REST/JSON, /api/v1/...
FastAPI ──── слой сервисов (бизнес-правила: перемещение, ремонт, статусы)
   │              │
   │              └── импорт CSV/XLSX, выгрузки, отчёты
SQLAlchemy ─── PostgreSQL
```

Структура репозитория:

```
backend/
  app/
    api/            # роутеры по сущностям
    models/         # SQLAlchemy-модели
    schemas/        # Pydantic-схемы
    services/       # бизнес-правила
    importers/      # разбор и проверка CSV/XLSX
    exports/        # Excel, PDF
    auth/           # вход, сессии, роли и права
  alembic/
  seed/             # генератор тестовых данных (раздел 6)
  tests/
frontend/
  src/pages, src/components, src/api
docs/
docker-compose.yml
```

Решения, которые закладываем сразу:

- **Права в одном месте.** У каждого эндпоинта есть зависимость `require(permission)`, роль берётся из `current_user`. Чтобы потом подключить SSO банка, достаточно заменить одну зависимость.
- **Вход.** `POST /api/v1/auth/login` проверяет пароль (argon2) и создаёт запись в `user_session`. Клиент получает cookie `HttpOnly; SameSite=Strict` (с доменом и HTTPS — ещё `Secure`). Сессия живёт 8 часов и продлевается при активности. Блокировка пользователя удаляет его сессии. Защита от перебора: после 5 неудачных попыток за 15 минут логин блокируется на 15 минут. Первый суперадмин создаётся при старте из переменных окружения сервера; в репозитории паролей нет.
- **Секреты** лежат только в `/opt/bank-erp/.env` на сервере и в GitHub Secrets. В репозитории — только `.env.example`.
- **Журнал изменений.** События SQLAlchemy (`before_flush`) пишут в `audit_log`, кто и что изменил. Для банка это обязательно, а стоит дёшево.
- **Бизнес-операции — отдельные эндпоинты, а не PATCH полей.** Например, `POST /atms/{id}/move` в одной транзакции закрывает старое размещение и открывает новое.

**Текущая локация** банкомата — это его открытое размещение (`placed_to is null`). Отдельно её не храним, берём через view `atm_current`. На 2 000 строк это бесплатно.

**Вычисляемые значения:** простой ремонта (`finished_at − started_at`), статус сертификата по дате (действует / истекает ≤ 90 дней / истёк; «на продлении» и «отозван» — вручную), окончание гарантии (дата покупки + гарантийный срок модели, если не задано вручную).

### 4.2. Бизнес-правила

1. **Перемещение.** Старое размещение закрывается датой `placed_from` нового. Новая дата не может быть раньше даты начала текущего размещения.
2. **Статусы.** Допустимые переходы задаются в коде: «На складе банка → В доставке → В установке → В эксплуатации ⇄ На ремонте / На ремонте у вендора → К списанию → Списан». При «Списан» обязательна дата вывода, размещение закрывается.
3. **Ремонт с заменой узла.** Старый узел получает `removed_at`, новый — `installed_at`. Если тип узла картридер, NFC-ридер или EPP, ставится `affects_certification = true`. Сертификаты, привязанные к снятому узлу, попадают в отчёт «требуют проверки».
4. **Импорт** идемпотентен: повторная загрузка того же файла ничего не дублирует, upsert идёт по `atm_code`.

## 6. Тестовые данные

Заказчик не может передать данные банка, поэтому генератор — полноценная часть проекта, а не вспомогательный скрипт. На его данных идут демо, тесты импорта и проверка производительности.

Требования:

- **Воспроизводимость.** Фиксированный `--seed`, объём задаётся `--count` (1 000 / 1 300 / 2 000 — по прогнозу роста сети).
- **Реалистичная география.** 14 регионов Узбекистана; доля Ташкента ~30 %, остальное — пропорционально населению. Реальные районы Ташкента и областные центры. Координаты — внутри границ районов, около центра населённого пункта. Улицы и ориентиры — из подготовленных списков, адреса вымышленные.
- **Реальные модели.** NCR SelfServ 22e / 25 / 84, Hyosung MX8300D / MX8600 / 9E, Diebold Nixdorf DN Series 200 / 250, GRG H68N. Паспортные данные — из спецификаций (раздел 7 набора полей).
- **Правдоподобные распределения:** около 85 % «В эксплуатации», несколько процентов на ремонте и на складе, единичные списанные. Даты покупки — за последние 8 лет. У 1–3 размещений на банкомат — история перемещений. Ремонты распределены по Пуассону, чаще у старых моделей, исполнители — 3 вымышленных вендора.
- **Процессинги.** Terminal ID и Merchant ID в трёх разных форматах (форматы условные). Часть банкоматов есть не во всех процессингах.
- **Сертификаты:** около 5 % истекают в ближайшие 90 дней, единичные — уже истекли, есть «требуют проверки» после замены картридера. Без этого дашборд будет пустым.
- **Три выхода:**
  1. наполнение БД напрямую (`python -m seed`);
  2. «чистый» CSV в формате раздела 5 набора полей — эталон для импорта;
  3. «грязный» CSV с типичными ошибками Excel: дубли кодов, неизвестная модель, «Ташкент» вместо «г. Ташкент», даты `15.03.2024`, запятая в координатах, пустые обязательные поля, координаты вне Узбекистана. На нём тестируем отчёт об ошибках импорта.

Все данные помечены как вымышленные: банк — «Банк X», вендоры — «Сервис-вендор 1–3».

## 8. Риски

| Риск | Что делаем |
|---|---|
| Нет реальных данных — структура может не совпасть с тем, как банк реально ведёт учёт | Генератор на основе согласованного набора полей; на демо проверяем с заказчиком, «узнаёт» ли он данные |
| Один разработчик, объём растёт | Жёсткий список «не делаем» (раздел 1) |
| Сервис в интернете по HTTP (нет домена) | Вход обязателен, перебор паролей ограничен, firewall открывает только 22/80/443, данные вымышленные. С доменом — HTTPS через Caddy |
| Сервер 1 ГБ RAM | Сборка только в GitHub Actions; лимиты памяти контейнеров; Postgres с небольшими `shared_buffers` |
| Репозиторий публичный | В git нет секретов, IP сервера и материалов заказчика (`docs/*.docx`, `*.pdf`, записи звонков — в `.gitignore`) |
| Открытые вопросы по процессингам (в одном или в трёх) | Модель `atm_processing` подходит для обоих ответов |
| Сертификаты в банке не собраны | В MVP — ручной ввод и загрузка сканов; отчёт «у кого нет сертификатов» |
